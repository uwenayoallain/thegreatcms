# Working in this repository

Notes for agents and humans arriving cold. For _using_ GreatCMS on a site, read
[SPEC.md](./SPEC.md) instead — this file is about changing GreatCMS itself.

## What this project is

A Git-backed CMS whose product is a **file standard**, not an application. The
studio and the packages are implementations of `SPEC.md`. When the two disagree,
`SPEC.md` is right and the code is a bug.

## Invariants — breaking one is a design change, not a fix

- **The studio never executes anything from a managed repository.** Not to build
  a preview, not to read a schema. Schemas are data, previews run on the site's
  own CI or the developer's machine.
- **A site never depends on the studio at runtime.** No network call, no
  database, no API key in a build. Shut the studio down and every site it
  managed keeps building from what is in Git.
- **A publish is one commit, or none.** Content and the images it references
  land together, through the Git Data API. Never the contents API, which is one
  commit per file.
- **A missing content file resolves to schema defaults**, so a site is correct
  before the CMS has ever run. A missing _schema_ file is a loud error.
- **The admin ships zero JavaScript.** Every mutation is a form POST, including
  adding and reordering blocks. This is what makes it accessible by
  construction, and it is asserted by tests.
- **Alt text is structurally required.** Only a field marked
  `alt: decorative-allowed` may store an empty one.
- **Nothing in a publish path may block on a model.** AI titles are opt-in,
  time-boxed, and always fall back to the diff-generated summary.

## Layout

```
SPEC.md                 the standard — the actual product
apps/studio/            the CMS: auth, editor, publishing, inbox
packages/spec/          schema parsing, validation, resolution rules
packages/git/           atomic commits and pull requests
packages/reader/        build-time reader for JS frameworks
packages/cli/           greatcms init / preview / doctor
packages/conformance/   fixtures + verifier proving a reader is correct
examples/               a real Astro site, and a Python reader
docs/                   generated agent surface — never edit by hand
```

## Working here

```sh
pnpm install
pnpm check      # lint, format, generated docs, typecheck, tests
```

- `pnpm check` is the gate. It must pass before anything is committed.
- Tooling is Rust where a Rust tool exists: **oxlint**, **oxfmt**, **tsdown**,
  **rolldown-vite**. Do not reintroduce ESLint, Prettier, or plain Rollup.
- `docs/` is generated by `pnpm run docs:build` from `SPEC.md` and `README.md`.
  Editing it directly will be overwritten and CI will fail.
- Changing the standard means bumping `version:` and documenting a migration.
  New optional keys and field types are additive within version 1; anything that
  changes how existing content _resolves_ is not.
- Prefer a test that would have caught the bug over a comment explaining it.
  Several of the tests here exist because they caught a real one: branch names
  containing slashes, alt text dropped on upload, a comment-only YAML section.
